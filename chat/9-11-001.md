我记得这个方向，而且我认为你现在的判断是对的：**表单引擎、报表引擎、图表引擎不是“过时 UI 技术”，而是从传统 ERP 过渡到 AGI 原生企业系统时，非常重要的一层“确定性人机确认层”。**

你现在实际上已经逐渐形成了三层不同性质的项目：

```text
EVO
= 企业事实、业务语义、Command、Ledger、Cost、Flow、Metric
= 企业运行时 / Enterprise Operating System

Form / Report / Chart Engines
= 把 EVO 的语义翻译成人可以确认、编辑、理解的交互结构
= Human Verification / Semantic Presentation Layer

Eidos
= AI-native Experience Runtime
= 把页面定义、交互定义、组件定义真正渲染出来
```

我很赞成把它们拆开，而不是全部塞进 EVO。

---

### 关键的一点：不要把“表单引擎”理解成传统低代码表单

如果只是：

```text
字段定义
→ 输入框
→ 下拉框
→ 日期控件
→ 提交
```

那它确实很容易在 AGI 时代被淘汰。

但你真正需要的其实不是普通 Form Engine，而是一个更高层的：

> **Semantic Interaction Engine**
>
> 语义交互引擎

“表单”只是它在当前阶段最重要的一种表现形式。

它的工作不是简单地把 JSON Schema 变成 HTML，而是：

```text
EVO Semantic Definition
        ↓
Interaction Interpretation
        ↓
Human Review Model
        ↓
Eidos Page Definition
        ↓
User Interaction
        ↓
Validated Intent
        ↓
EVO Command
```

所以它真正承担的是：

> **把机器理解的企业语义，转换成人类可以检查、确认、补充和授权的交互。**

这在现在和未来几年都非常重要。

---

## 为什么 AGI 越强，这一层反而越重要

很多人会直觉认为：

```text
AGI 足够强
→ 不需要表单
→ 直接跟 AI 说话
```

我认为这是不完整的。

真正企业环境里，至少有五类场景不会因为 AI 变强就消失：

```text
确认
审批
责任
审计
高密度结构化信息浏览
```

比如 AI 帮你创建采购订单：

用户可能说：

> 帮我给供应商 A 下单 5000 个 P-100，下周交货。

AI 可以理解。

但在真正提交之前，用户可能还是需要看到：

```text
Supplier      A
Item          P-100
Qty           5000
Price         3.42
Currency      USD
Warehouse     HK
Delivery      2026-09-18
Tax           ...
Payment Term  Net 30
Project       HW-2026-003
Profit Center PC-HW
```

并明确：

```text
[确认提交]
```

这不是因为 AI 不够聪明。

而是因为：

> **人必须知道自己究竟授权了什么。**

因此未来不是：

```text
AI 替代 UI
```

而更可能是：

```text
AI 生成交互
+
结构化 UI 负责确认
+
Command 负责最终执行
```

这正好和 EVO 已经确定的原则完全一致：

```text
AI may propose
Human / Policy may approve
Actual business execution must use Command
```

# 我建议我们重新定义 Eidos 的位置

我以前把 Eidos 偏向理解为“前端框架”，现在我认为应该进一步提升定义。

Eidos 不应该成为：

> EVO 的前端。

而应该成为：

> **AI-native Interaction Runtime**

也就是说 Eidos 不理解：

```text
销售订单
采购订单
库存
应收
利润中心
```

它只理解一种通用的交互协议，例如：

```text
Page
Section
Field
Table
Action
Chart
Metric
Prompt
Confirmation
WorkItem
Navigation
State
Permission
```

例如：

```text
EVO
知道：
SalesOrder.quantity

Form Engine
知道：
这是数量字段
required
min = 1
unit = EA
business meaning = ordered quantity

Eidos
知道：
把它渲染为 NumberInput
```

这样依赖方向就非常干净：

```text
EVO
   ↓ semantic metadata
Interaction Engines
   ↓ UI definition
Eidos
   ↓ rendered experience
Human
```

而不是：

```text
Eidos → 直接懂 ERP
```

这一点非常重要。

# 中间这一层，我建议不要只有一个“表单引擎”

长期看应该形成一个：

> **EVO Experience Compiler Layer**

可以先分为四个引擎：

```text
Form Engine
Report Engine
Chart Engine
Workspace Engine
```

以后再增加：

```text
Dashboard Engine
Mobile Interaction Engine
Scanner Interaction Engine
Approval Engine
AI Confirmation Engine
```

但这些不一定都是独立服务。

概念上独立即可。

---

## 1. Form Engine

负责：

```text
EVO ApplicationDefinition
FieldDefinition
CommandDefinition
Validation Rules
Permissions
Business Context
        ↓
Form Definition
```

比如 EVO 给：

```json
{
  "field": "quantity",
  "semanticType": "Quantity",
  "unit": "EA",
  "required": true,
  "min": 1
}
```

Form Engine 产生：

```json
{
  "component": "NumberField",
  "label": "Quantity",
  "required": true,
  "unitAdornment": "EA",
  "validation": {
    "min": 1
  }
}
```

Eidos 负责渲染。

---

## 2. Report Engine

Report Engine 不应该只是 SQL 报表。

它应该读取：

```text
MetricDefinition
LedgerDefinition
DimensionDefinition
FlowDefinition
BusinessObjectDefinition
```

然后生成：

```text
Rows
Columns
Grouping
Aggregation
Filter
Drill-down
Lineage
```

比如：

```text
项目利润分析

Rows:
Project

Measures:
Revenue
COGS
R&D Expense
Gross Profit
Operating Profit

Dimensions:
Department
Profit Center
Product
Region
Period
```

这和我们刚才讨论的 Project / Profit Center / Department Dimension 会直接连接起来。

---

## 3. Chart Engine

Chart Engine 也不要自己理解业务。

它接受：

```text
Metric Query Result
+
Visualization Intent
```

例如：

```text
Metric:
Inventory Turnover

Dimensions:
Month

Intent:
Trend
```

生成：

```text
LineChart
```

如果：

```text
Actual vs Target
```

生成：

```text
Bullet / Variance / Bar
```

所以：

```text
Metric Engine
负责“数字是什么意思”

Chart Engine
负责“怎样表达这个数字”

Eidos
负责“怎样画出来”
```

三者不要混。

# 我认为最重要的新概念，是“Interaction Definition”

我们不应该让 Form Engine 直接生成 Eidos 私有组件 JSON。

否则以后 Eidos 改了，Form Engine 全部跟着改。

应该多一层稳定协议：

```text
EVO Semantics
      ↓
Interaction Definition
      ↓
Eidos Adapter
      ↓
Eidos
```

可以称：

> **EID — Eidos Interaction Definition**

或者更加项目无关一点：

> **UIDL — User Interaction Definition Language**

我更倾向第二种。

例如：

```json
{
  "type": "form",
  "purpose": "execute-command",
  "command": "approve-sales-order",
  "sections": [
    {
      "title": "Order",
      "fields": [
        {
          "key": "customer",
          "semanticType": "CustomerRef",
          "required": true
        },
        {
          "key": "quantity",
          "semanticType": "Quantity",
          "required": true
        }
      ]
    }
  ],
  "actions": [
    {
      "type": "submit",
      "command": "approve-sales-order"
    }
  ]
}
```

Eidos 再负责：

```text
CustomerRef → SearchSelect
Quantity → NumberInput
Submit → PrimaryActionButton
```

这样未来即使 Eidos 被完全重写，Interaction Definition 仍然存在。

# 这也是为什么 Eidos 必须独立

你的要求：

> Eidos 文档本身不能依赖任何 LLM 聊天记录

我完全赞同，而且现在应该让 Eidos 和 EVO 使用同一种“LLM Context Determinism”工程规范。

也就是说 Eidos 自己应该有：

```text
PHILOSOPHY.md
CONCEPTS.md
INVARIANTS.md
ARCHITECTURE.md
PUBLIC-API.md
LLM.md
context.manifest.json
```

它不能靠：

> “之前 ChatGPT 说 Eidos 是干什么的”

才能理解项目。

一个新的模型 clone repo 后，应该很快得到：

```text
Eidos 是什么
Eidos 不是什么
它拥有哪一层
它不能访问哪一层
输入协议是什么
输出/事件协议是什么
组件系统是什么
状态模型是什么
插件模型是什么
```

例如 Eidos 的核心 invariant 我现在就能先定几个：

```text
EIDOS-01
Eidos never owns enterprise business truth.

EIDOS-02
Eidos does not write EVO BusinessData directly.

EIDOS-03
All actual business actions go through declared Command contracts.

EIDOS-04
Eidos renders Interaction Definitions; it does not infer enterprise semantics.

EIDOS-05
Components are replaceable implementations behind stable semantic component contracts.

EIDOS-06
Page definitions must be serializable, versionable and reproducible.

EIDOS-07
An AI-generated interface is Draft until validated or accepted under policy.

EIDOS-08
Rendered state must never become the authoritative business state.
```

这会非常稳。

# 三个项目的边界因此非常明确

```text
EVO
“What does the enterprise mean and what may happen?”
企业是什么、业务是什么、允许执行什么。

Experience Compiler
“How should this meaning become an interaction?”
这些语义应该如何变成人类可操作、可确认的结构。

Eidos
“How is that interaction rendered and executed?”
这些交互结构怎样真正显示和运行。
```

这三个层级我认为非常漂亮。

甚至未来可以这样定义：

```text
EVO = Semantic Runtime
Experience Compiler = Interaction Compiler
Eidos = Experience Runtime
```

还有一个我认为特别有价值的方向：

**EVO 不应该返回“页面”。**

EVO 应该返回：

```text
ApplicationDefinition
CommandDefinition
FieldDefinition
MetricDefinition
Permission
State
```

由 Experience Compiler 决定：

> 这个人在这个设备、这个角色、这个任务上下文下，应该看到什么。

比如同一个 `ShipOrder`：

仓库电脑：

```text
完整表单
```

PDA：

```text
扫码 → 数量 → 确认
```

手机：

```text
极简卡片
```

AI：

```text
tool schema
```

API：

```text
JSON contract
```

但最后都是：

```text
ShipOrder Command
```

这就是我们之前一直说的：

> **Application / Tool is not the business itself.**

它和你今天提出的 Eidos + Form Engine 架构实际上完全衔接上了。

**这个设计不是为了“暂时撑到 AGI 来了再扔掉”。**

但如果把它设计成：

> **Semantic Interaction / Experience Compiler**

那么它反而是 EVO 从当前 LLM 时代进入更强 Agent/AGI 时代的一条核心桥梁。

最终可能演化成：

Enterprise Meaning
      ↓
AI
      ↓
Generative Interaction
      ↓
Human / Agent Verification
      ↓
Deterministic Command

> **EVO 负责企业的意义与事实，Experience Compiler 负责把意义编译成交互，Eidos 负责运行交互。**
