这一步非常值得讨论，而且我认为应该**先把市场定位和商业模式定下来，再继续把 v0.9 往产品化方向做**。因为技术架构已经足够清楚，接下来“为谁做、卖什么、怎么收费”会反过来决定产品体验、部署模式、模板市场、AI 能力甚至开源策略。

我刚刚也重新看了一下 2026 年 ERP/AI ERP 市场。一个很重要的信号是：主流 ERP 基本都已经在讲 AI，SAP、Oracle、Microsoft、NetSuite 等都已经有 Copilot/Agent 类能力；同时 Rillet、DualEntry、Campfire、Light 等所谓 AI-native ERP 也快速出现。([ERP Research][1])

所以我认为 **EVO 绝对不能把自己定位成“一个带 AI 的 ERP”**。这个定位到 2026 年已经没有足够区分度。

## 我现在对 EVO 的市场定位

我会把 EVO 定义成：

> **EVO = AI-Native Enterprise Operating System**
>
> **不是给企业提供一套固定 ERP，而是提供一个可以根据企业业务自动生长、持续演化的企业运行系统。**

这和我们现在做出来的底层架构其实高度一致。

传统 ERP 的逻辑大致是：

```text
软件公司
   ↓
预先定义模块
   ↓
销售 / 采购 / 库存 / 生产 / 财务
   ↓
实施顾问
   ↓
配置 + 二开
   ↓
企业适应 ERP
```

EVO 应该反过来：

```text
企业
 ↓
描述自己怎么经营
 ↓
AI 理解业务
 ↓
Metadata / App / Field / Command
 ↓
Posting / Ledger / Work / Process
 ↓
生成企业运行系统
 ↓
企业继续变化
 ↓
AI + Version / Migration / Replay
 ↓
系统跟着企业变化
```

这才是 EVO 真正值得做的东西。

而且这个方向和现在市场上的很多 “AI-native ERP” 仍然不同。目前被归为 AI-native ERP 的新公司，相当一部分仍然以**财务/总账为中心**，重点替代 NetSuite、Sage Intacct、QuickBooks；也已经出现像 Doss 这样更偏库存、订单、采购的 operations-first 产品。([ERP Research][2])

而 EVO 从一开始就在做：

```text
Metadata
+
BusinessData
+
Posting
+
Generic Ledger
+
Cost
+
Process / Work
+
AI Command
```

所以我们的野心可以更大：

> **不是 AI Accounting。**
>
> **不是 AI ERP。**
>
> **而是企业软件的生成与运行平台。**

---

## 但第一批客户不能是“所有企业”

这是商业上非常重要的一点。

技术架构可以：

> Industry Agnostic

但市场定位不能：

> Everybody.

如果网站首页写：

> “适用于所有行业的下一代 AI ERP”

基本很难卖。

我会把**第一阶段 ICP** 定在：

> **20～500 人、业务正在快速变化、已经被 Excel + SaaS + 老 ERP + 自研系统割裂的成长型企业。**

特别是这些企业：

```text
业务流程变化快
+
现成 ERP 不完全适配
+
大量 Excel
+
大量人工协调
+
已有一些 SaaS
+
开始出现跨部门数据问题
+
又承担不起 SAP 级实施成本
```

这是 EVO 最容易体现价值的地方。

因为小微企业有 Odoo、ERPNext 等非常便宜甚至免费的方案。ERPNext 本身可以免费 self-host，商业成本主要来自托管和实施；Odoo/ERPNext 已经把传统 SME ERP 的价格压得很低。([Frappe][3])

所以 EVO **不要去打“更便宜的 ERP”这场战争。**

我们应该打的是：

> **“传统 ERP 做不到这么快地适应你的企业。”**

---

# 商业模式，我会设计成四层

我不建议单纯：

```text
$49/user/month
```

因为这会把 EVO 又变成传统 SaaS。

EVO 更适合：

```text
Platform
+
Enterprise Runtime
+
AI Consumption
+
Ecosystem
```

第一层是 **EVO Platform Subscription**。

按照企业规模/运行能力收费，而不是简单按照员工人数收费。例如以后可以形成：

```text
EVO Start
EVO Growth
EVO Enterprise
```

计费维度可以逐渐围绕：

```text
Enterprise 数量
BusinessData 规模
Automation 数量
AI Usage
高级治理能力
SLA
```

而不是：

```text
一个仓库管理员 = 一个 License
一个生产员工 = 一个 License
```

我尤其不喜欢传统 ERP 的 seat tax。

企业数字化越深入，用户越多，软件费用线性爆炸，实际上是在惩罚客户使用系统。ERPNext现在甚至明确把“no per-user pricing / compute-based pricing”作为卖点。([Frappe][3])

---

第二层是 **AI Consumption**。

但是这里不能简单做：

```text
Token × 价格
```

现在 AI 软件商业模式已经开始暴露一个问题：纯 token/usage 计费容易让企业预算不可预测，企业开始要求更明确的成本治理。([TechRadar][4])

EVO 更适合把 AI 计量抽象成：

```text
AI Credits
```

底层可以接：

```text
OpenAI
Anthropic
Google
Local Model
Enterprise-owned Model
```

企业看到的是：

```text
AI Usage
AI Budget
AI Cost Center
AI Agent Cost
AI ROI
```

甚至未来 EVO 自己的 Ledger 就可以记录 AI 成本。

这个特别有意思：

> **EVO 可以用 EVO 自己核算 AI Agent 的经营成本。**

例如：

```text
采购 Agent
本月执行 18,392 次
↓
模型成本 $1,260
↓
自动完成采购任务 8,920 个
↓
人工介入 312 个
↓
平均任务成本 $0.14
```

这会成为企业真正管理 AI Workforce 的基础。

---

第三层我认为是未来非常重要的：

# EVO App / Template Marketplace

因为我们现在的架构天然支持：

```text
Model
 ↓
Template
 ↓
Application Definition
 ↓
Enterprise Instance
 ↓
Enterprise Overlay
```

所以将来第三方不应该主要“写插件”。

他们应该发布：

```text
Application Template

Posting Template

Process Template

Industry Template

AI Agent Template

Integration Template
```

例如：

```text
跨境电商套件
制造业套件
贸易公司套件
SaaS 公司套件
仓储套件
订阅计费套件
香港财务模板
新加坡财务模板
美国 GAAP 模板
```

企业点击：

> Install

EVO 根据企业 Metadata 安装。

再由 AI：

```text
Template
+
企业现状
+
Enterprise Overlay
=
企业自己的版本
```

这时候我们才真正实现你最早提出的：

> **业务像 APP 一样安装。**

商业模式就变成：

```text
开发者 / 顾问
        ↓
EVO Marketplace
        ↓
Template / App / Agent
        ↓
企业购买
        ↓
70% Developer
30% EVO
```

比例以后当然可以调整。

这会比单纯卖 ERP license 有意思得多。

---

第四层，是我认为可能最终价值最大的：

# EVO Enterprise Cloud

最终我们卖的其实不是软件安装包。

而是：

```text
EVO Cloud
```

客户注册企业：

```text
Create Enterprise
```

然后 AI 问：

```text
你们公司是做什么的？

现在怎么接订单？

库存在哪里？

采购怎么做？

什么时候安排生产？

什么时候确认收入？

谁负责审批？

现在使用哪些系统？
```

客户可以上传：

```text
Excel
旧 ERP 导出
SOP
合同
表单
数据库
API
```

然后：

```text
AI
 ↓
理解企业
 ↓
生成 Metadata
 ↓
推荐 Templates
 ↓
生成 Applications
 ↓
生成 Commands
 ↓
生成 Posting Rules
 ↓
生成 Workflows
 ↓
Sandbox Simulation
 ↓
用户确认
 ↓
Publish
```

这才是我心里真正的 EVO。

不是：

> “请联系我们的实施顾问，实施周期 6 个月。”

而是：

> **Tell EVO how your company works.**

甚至最终：

> **Show EVO how your company works.**

Software

## 有一个商业决定，我现在反而不建议过早做

就是：

> **开源还是闭源。**

EVO 的技术架构确实非常适合开放生态。

但我现在不会简单选择：

```text
全部闭源
```

也不会简单选择：

```text
全部 GPL
```

我更倾向未来研究一种：

```text
Open Contracts / SDK
Open Template Format
Open Command Schema
Open Integration Protocol
Open Developer Tooling

        +

Commercial EVO Cloud
Commercial Enterprise Runtime
Commercial AI Control Plane
Commercial Marketplace
Commercial Governance
```

也就是说：

> **开放 EVO 生态标准，而不是轻易把整个商业护城河定义成源代码许可证。**

因为真正的护城河最终应该是：

```text
Enterprise Metadata Network
+
Templates
+
AI Business Understanding
+
Migration Intelligence
+
Enterprise Runtime
+
Developer Ecosystem
```

而不是“别人看不到我的 TypeScript”。

---

## 最关键的是：EVO 不应该卖“AI”

这是我对市场定位最想坚持的一点。

2026 年所有人都可以说：

> AI ERP / Agentic ERP / AI Copilot。

市场研究甚至已经指出，“AI-powered ERP”这个标签现在涵盖的东西差异极大，从外挂聊天机器人到真正执行多步骤流程的 Agent 都被放在同一个标签下。([ERP Research][5])

所以 EVO 首页未来不应该把核心口号写成：

> **AI-Powered ERP**

我更倾向：

> **EVO — The Operating System for Your Enterprise.**

下面一句：

> **Your business defines the system. Not the other way around.**

然后 AI 是为什么 EVO 能做到这一点的**技术原因**，而不是商品本身。

因为真正的产品价值是：

```text
过去：

企业变化
↓
提需求
↓
顾问
↓
开发
↓
测试
↓
上线
↓
3个月


EVO：

企业变化
↓
描述变化
↓
AI理解
↓
模拟影响
↓
生成 Change Set
↓
Replay / Validation
↓
Gray Release
↓
上线
```

如果最后我们真能把这个闭环做到可靠，**这才是 EVO 最大的商业价值。**

而且你之前坚持的“业务历史保留、重新记账、成本重算、版本化、灰度升级、不能相信人和 LLM 的记忆”，现在看已经不只是技术洁癖。

它们实际上构成了一个非常强的商业能力：

> **让企业敢于让 AI 修改自己的 ERP。**

这是普通“AI 帮我生成几个表单”的产品很难跨过去的一道门槛。
