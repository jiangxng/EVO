# EVO-00 — Core Architecture & Domain Model

**Version:** 0.1  
**Status:** Draft

## 1. Project Vision

EVO is an AI-native Enterprise Operating System.

EVO models an enterprise as a set of business definitions,
business applications, business facts, events, rules, processes,
ledgers and calculations.

Business facts are immutable.

Business results are reproducible.

Accounting can be replayed using different rule versions.

Costs can be recalculated from newly generated accounting data.

AI is a native participant in the system rather than an external assistant.

## 2. Core Architecture

```text
                         EVO
                          │
        ┌─────────────────┼─────────────────┐
        │                 │                 │
        ↓                 ↓                 ↓
     Metadata           Runtime             AI
        │                 │                 │
   ┌────┼────┐       ┌────┼────┐            │
   ↓    ↓    ↓       ↓    ↓    ↓            │
Domain  TT  App     Event Rule Ledger        │
              │                  │            │
              ↓                  ↓            │
          Field Groups       Balance          │
              │                  │            │
              ↓                  ↓            │
            Fields          Calculation       │
                                 │            │
                                 ↓            │
                               Cost ←─────────┘
```

`TT = Transaction Type`

The conceptual hierarchy is:

```text
Domain
  ↓
Transaction Type
  ↓
Specific Business Application
  ↓
Field Group
  ↓
Field
```

Transaction Type is a high-level abstraction of a business application category.
It is not the same thing as a specific business application.

## 3. Business Runtime

The real-time business execution path is:

```text
Business Fact
      │
      ↓
Business Event
      │
      ↓
Conditional Posting
      │
      ↓
Ledger Entries
      │
      ↓
Balance / Projection
      │
      ↓
Business State / Plan / Work
```

`Posting Run` is not a mandatory step for every real-time business event.
It represents a posting execution/recalculation run, especially for historical
replay or batch processing.

## 4. Historical Replay / Re-posting

Historical business facts remain unchanged.

Different versions of posting rules can be applied to the same historical
business facts to generate different accounting datasets.

```text
                  Historical Business Facts
                           │
                 ┌─────────┴─────────┐
                 ↓                   ↓
          Posting Rule v1      Posting Rule v2
                 ↓                   ↓
          Posting Run #1       Posting Run #2
                 ↓                   ↓
          Ledger Dataset #1    Ledger Dataset #2
```

The original business facts are not modified by replay.

## 5. Cost Recalculation

Cost is calculated from accounting / ledger data and can be recalculated
when a new ledger dataset or a new valuation policy is used.

```text
Ledger Dataset
      │
      ↓
Cost / Valuation Policy
      │
      ↓
Cost Run
      │
      ↓
Cost Dataset
      │
      ├── Inventory Value
      ├── Production Cost
      ├── COGS
      ├── Gross Margin
      └── Financial / Management Analysis
```

Cost Dataset is a calculation result, not an immutable business fact.

## 6. Fundamental Principles

### 6.1 Business Facts are Immutable

Business facts represent what actually happened in the business.
Subsequent execution should not rewrite the original historical fact.

### 6.2 Business Results are Reproducible

Business results should be capable of being regenerated from their source
facts and the rules used to calculate them.

### 6.3 Accounting is Reproducible

Accounting results can be regenerated by applying a specified version of
posting rules to historical business facts.

### 6.4 Costs are Recalculable

Cost results can be regenerated from a specified ledger dataset and
cost / valuation policy.

### 6.5 Ledger is Not Finance-only

Ledger is a general business abstraction.

Examples include:

- 待下单
- 待采购
- 待生产
- 待质检
- 待入库
- 待出库
- 待收款
- 待付款
- 库存
- 应收
- 应付
- 收入
- 费用

Financial accounting is a standardized family within the broader ledger model.

### 6.6 Transaction Type is Not Specific Application

For example:

```text
销售订单
    │
    ├── 预售销售
    ├── 现货销售
    └── 寄售销售
```

`销售订单` is the Transaction Type.

`预售销售`、`现货销售`、`寄售销售` are examples of specific business
applications under that Transaction Type.

Different applications under the same Transaction Type may have different
fields, operations, processes, rules and ledger effects.

### 6.7 AI is Native

AI is not merely an external assistant attached to EVO.

AI should be able to understand and operate against EVO's metadata, business
data, events, rules, processes and ledgers.

### 6.8 UI is Not the Core

Eidos may serve as a frontend / application runtime, but EVO's business
model must remain independent of the UI framework.

## 7. Open Questions

The following questions are intentionally not finalized in EVO-00.

1. Is Ledger Dataset an independent accounting dataset, a versioned
   calculation result, or a projection/view?

2. What is the exact relationship between Business Fact, Business Event and
   Ledger Entry?

3. How are real-time posting and historical replay unified?

4. How are multiple Posting Rule versions selected?

5. Can multiple Ledger Datasets coexist and be compared?

6. How does Cost Dataset depend on Ledger Dataset?

7. Which results are immutable facts and which are projections?

8. What is the exact relationship between Model, Template, Application and
   Enterprise Application Instance?

## 9. 2026-09-22 Addendum — 业财一体与可安装能力边界

本节是对前述 Core Architecture 的增量澄清，不替代已有内容。

### 9.1 EVO 不是财务平台

EVO 的核心定位不是：

```text
Finance Platform
+ Business Modules
```

也不是：

```text
Business System
→ Financial Interface
→ Separate Finance System
```

更准确的定位是：

> **EVO 是以企业事实为源头，通过条件式记账、账本抽象、关系、Projection 和可安装应用，把企业业务运行与财务解释统一在同一套可重放、可演进的企业运行底座上。**

因此：

```text
Enterprise Business
→ BusinessData
→ Conditional Posting / Rules
→ Operational / Economic Ledgers
→ Balances / Work / Cost / Settlement

same canonical facts
→ Accounting Recognition
→ General Ledger
→ Trial Balance
→ Financial Statements
```

“业财一体”表示业务与财务共享同一事实来源和可追溯规则链，并不表示所有业务账本都必须成为会计科目。

### 9.2 平台提供原语，应用提供业务语义

Core / Platform 应稳定提供：

```text
Command
BusinessData
Relationship / Lineage
Posting
Ledger
Balance
Allocation
Valuation
Replay
Work / Projection
Permission / Capability
Versioning / Migration / Audit
```

具体企业能力优先由可安装对象提供：

```text
Application
Application Package
Business Pack
Plugin
Enterprise Template
Industry Package
Accounting / Reporting Package
```

例如：

```text
Sales
Procurement
Production
Inventory
Collection
Payment
Sales Return
Exchange
Revenue Recognition
Cost Recognition
Expense Accrual
Fixed Asset
General Ledger
Tax
Financial Reporting
```

不应仅因为某项能力常见于传统 ERP，就把其业务逻辑固化进 EVO Core。

### 9.3 条件式记账是业务与财务连接器

Application 决定：

```text
what business means
what event occurred
what conditions are satisfied
```

Posting Rule 决定：

```text
what ledger/accounting effects follow
under which conditions
with which dimensions
using which policy/version
```

因此，类似“确认收入”这类能力可以由具体应用或可安装包在满足条件时触发会计确认，而不是由 Core 写死某一业务时点。

### 9.4 企业复杂度优先增长在 Metadata / App / Rules，而不是 Core

目标关系：

```text
More enterprise capability
≈
more installable definitions + events + rules + ledgers + projections
```

而不是：

```text
More enterprise capability
=
more hard-coded runtime branches
```

只有现有通用原语无法满足已经确认的当前业务验收条件时，才允许新增 Core abstraction.

### 9.5 业财一体的最低可解释链

任何正式业务/财务结果最终应可追溯：

```text
Result
→ Ledger / GL Line
→ Posting / Accounting Rule Version
→ BusinessData
→ Enterprise Business Event
```

财务报表、管理报表和 Work 不得成为脱离企业事实的第二套真相。
