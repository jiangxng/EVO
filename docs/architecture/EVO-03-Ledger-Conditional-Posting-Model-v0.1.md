# EVO-03 — Ledger & Conditional Posting Model

**Version:** 0.1  
**Status:** Draft / Architecture Design  
**Project:** EVO — Enterprise Operating System

---

## 1. Purpose

EVO-03 defines the generic posting and ledger model shared by operational and financial accounting.

> **A Ledger is a continuous record of a business quantity, amount, obligation, state, plan or accounting measure.**

Financial accounting is one standardized ledger family, not the entire ledger model.

---

## 2. Core Runtime Flow

```text
Business Data
    ↓
Posting Input
    ↓
Posting Sequence
    ↓
Conditional Posting
    ↓
Ledger Entries
    ↓
Ledger Balance
    ↓
Business State / Plan / Work
```

---

## 3. Ledger Definition vs Ledger Entry

### Ledger Definition

Metadata describing what a ledger means.

Examples:

```text
待生产
待采购
待入库
待出库
待收款
待付款
库存数量
库存价值
现金
应收账款
应付账款
营业收入
待审批
```

### Ledger Entry

A runtime result generated by posting.

Example:

```text
Ledger: 待生产
Quantity: +70
Source: Sales Order Approval
```

Therefore:

```text
Ledger Definition ≠ Ledger Entry
```

## 5. Conditional Posting

Conditional Posting determines which ledger effects a Posting Input creates.

```text
Application
+ Posting Input
+ Business Conditions
        ↓
Posting Rule
        ↓
Ledger Effects
```

A rule may define:

```text
Target Ledger
Direction
Quantity Formula
Amount Formula
Conditions
Dimensions
Priority
Rule Version
```

---

## 6. Application-Specific Behavior

Example:

### 预售销售

```text
Approval:
    待生产 +100
    待出库 +100
    待收款 +amount
```

### 现货销售

```text
Approval:
    待出库 +100
    待收款 +amount
```

Both may belong to:

```text
Transaction Type = 销售订单
```

Transaction Type provides shared semantic identity; the specific application determines actual posting behavior.

---

## 7. Posting Conditions

A rule may inspect:

```text
Current application fields
Related fields
Referenced objects
Current balances
Enterprise policy
Organization
Warehouse

Product type
Threshold
Currency

```

Example:

```text
IF 商品类型 = 自制品
THEN
    待生产 + quantity
    待出库 + quantity
    待收款 + amount
```

```text
IF 商品类型 = 外购品
THEN
    待采购 + quantity
    待入库 + quantity
    待出库 + quantity
    待收款 + amount
```

## 8. Ledger Entry

Conceptually:

```text
LedgerEntry
    enterprise
    ledger
    posting_input
    posting_rule_version
    posting_sequence
    dimensions
    quantity
    amount
    unit
    currency
    effective_time
```

Physical schema remains deferred.

Ledger Entry is a reproducible posting result, not original business data.

---

## 9. Ledger Dimensions

A ledger may be partitioned by explicit dimensions.

Examples:

```text
Enterprise
Organization
Warehouse
Product
Customer
Supplier
Project
Batch
Serial Number
Currency
Application
Transaction Type
```

Example:

```text
Ledger = 库存数量
Warehouse = HK
Product = A
Balance = 125
```

Dimensions must be explicit metadata rather than hidden in application SQL.

---

## 10. Quantity and Amount

A Ledger Entry may contain:

```text
Quantity only
Amount only
Quantity + Amount
```

Examples:

```text
待生产
quantity = +70
```

```text
现金
amount = +10000
```

```text
库存
quantity = +100
amount = +1200
```

Cost values that depend on valuation policy should remain recalculable rather than permanently embedded as immutable source facts.

---

## 11. Direction

The generic ledger model uses semantic increase/decrease:

```text
+ increase
- decrease
```

Financial ledger definitions may additionally expose:

```text
Debit
Credit
```

EVO does not force every operational ledger into debit/credit terminology.

---

## 12. Balance

Balance is derived from Ledger Entries.

```text
Balance = Σ Ledger Entries
```

Example:

```text
待生产
+70
-30
----
40
```

Balance is a projection/result.

It may be materialized for performance but is not the historical source.

---

## 13. Ledger-Driven State

Example:

```text
Sales Order Approved
      ↓
待生产 +70
      ↓
Balance = 70
      ↓
Production Plan
      ↓
Produce 30
      ↓
待生产 -30
      ↓
Balance = 40
```

The balance can drive:

```text
Work Queue
Plan
Alert
AI Recommendation
Next Command
```

without requiring one mutable status/quantity field to carry all historical meaning.

---

## 14. Posting Rules Are Versioned Metadata

Conceptually:

```text
PostingRule
    id
    application
    trigger
    condition
    ledger
    direction
    quantity_formula
    amount_formula
    dimension_mapping
    priority
    version
```

Published rule versions should be immutable.

Changing posting behavior creates a new rule version.

---

## 15. Rule Execution

For each Posting Input:

```text
1. Resolve Application Definition
2. Resolve applicable Posting Rule Version
3. Evaluate rules in deterministic order
4. Evaluate conditions
5. Calculate quantity / amount
6. Resolve ledger dimensions
7. Generate Ledger Entries
8. Update or rebuild materialized balances
```

The same input and rule version must generate the same entries.

---

## 16. Rule Order

When multiple rules apply to one input, rule execution must also be deterministic.

```text
Input Posting Sequence
+
Rule Priority
+
Stable Rule Sequence
```

This matters when later rules depend on balances affected by earlier rules.

---

## 17. Ledger Does Not Interpret Corrections

If business data produces:

```text
Original +100
Later adjustment -20
```

the ledger posts:

```text
+100
-20
```

The ledger does not need to know that the second record corrects the first.

That interpretation belongs to the business-description layer.

---

## 18. Replay

During full replay:

```text
Pause Real-Time Posting
      ↓
Clear Existing Ledger Entries
      ↓
Clear Materialized Balances
      ↓
Read All Posting Inputs
      ↓
Sort by Posting Sequence
      ↓
Apply Posting Rules
      ↓
Generate Ledger Entries
      ↓
Rebuild Balances
```

Cost results are recalculated in the valuation phase defined by EVO-04.

---

## 19. Ledger Dataset

EVO keeps `Ledger Dataset` as a conceptual reproducibility boundary.

```text
Business Data
+ Posting Rule Version
+ Posting Sequence
        ↓
Posting Run
        ↓
Ledger Dataset
```

In the initial implementation, a full replay may simply replace the active posting result set.

The abstraction remains useful for future versioning, comparison and audit.

---

## 20. Separation from Cost

Ledger and valuation are distinct concerns.

```text
Posting
    ↓
Ledger Entries
    ↓
Cost / Valuation Engine
    ↓
Cost Results
```

The Ledger Engine answers:

> Which ledger and dimensions receive what quantity or direct amount?

The Cost Engine answers:

> At what valuation should cost-bearing flows be measured?

FIFO, LIFO, average valuation and specific identification therefore belong to EVO-04.

## 21. Inventory Example

Business sequence:

```text
Purchase Receipt 100
Production Receipt 30
Sales Shipment 80
```

Possible posting:

```text
库存数量 +100
待入库 -100

库存数量 +30
待生产 -30

库存数量 -80
待出库 -80
```

The Cost Engine later determines the cost of the `库存数量 -80` flow using the selected valuation policy.

## 22. Financial Accounting as a Ledger Family

Financial posting can use the same infrastructure.

Example:

```text
Sales Invoice
    ↓
应收账款 +amount
营业收入 +amount
```

Financial definitions may layer debit/credit semantics and accounting standards on top of the generic ledger engine.

## 24. Architectural Decisions Locked by EVO-03

1. Ledger Definition is metadata.
2. Ledger Entry is runtime posting output.
3. Ledger Entries are generated from ordered Posting Inputs.
4. Posting Rules are explicit and versioned.
5. Posting Rule execution is deterministic.
6. Ledger may carry quantity, amount or both.
7. Ledger dimensions are explicit metadata.
8. Balance is derived from entries.
9. Ledger does not require correction relationships.
10. Financial and operational ledgers share one generic posting foundation.
11. Cost valuation is a separate calculation concern.
12. Posting results must be fully rebuildable.
