# ADR — Economic Runtime Architecture Freeze v0.1

**Status:** ACCEPTED / ARCHITECTURE FREEZE  
**Date:** 2026-09-18  
**Scope:** EVO Economic Runtime — facts, measurements, allocation, cost basis, valuation, projection, materialization, replay  
**Branch:** `evo/apm-certification-enterprise-template-v0.1`

## 0. Decision

EVO freezes the Economic Runtime around a strict separation between:

`Canonical Business/Economic Evidence`
` → Deterministic Interpretation`
` → Projection`
` → Rebuildable Materialization`

The runtime MUST preserve immutable business/economic facts and explicit business instructions while allowing allocation, cost, valuation, ledger/accounting consequences and current balances to be recalculated under pinned versioned definitions.

This ADR promotes the semantic conclusions proven by:

- `AP-FX-001-FOREIGN-CURRENCY-SETTLEMENT.md`
- `AP-MANUAL-ALLOC-001.md`
- `AP-COST-METHOD-001.md`
- `AP-RECALC-001.md`
- `BATCH-05-RUNTIME-ALLOCATION-COST-GENEALOGY.md`

It converges, rather than replaces, existing EVO-03 / EVO-04 / EVO-05 and valuation-posting implementation assets.

---

# 1. Constitutional runtime chain

The frozen semantic chain is:

`Business/Economic Fact`
` → Measurement / Explicit Basis Evidence / Explicit Allocation Instruction`
` → Position / Allocation / Derivation`
` → Cost Basis / Valuation`
` → Operational or Accounting Projection`
` → Materialized State / Read Model / Checkpoint`

Not every business event uses every stage.

Examples:

- pending-production quantity may project directly from fact to operational ledger;
- FIFO inventory valuation uses position → allocation → cost basis → valuation;
- moving-average valuation uses a valuation pool rather than receipt-layer allocation;
- FX settlement uses a foreign position + settlement allocation → realized FX result;
- FX period close uses an open foreign position + period-end rate dataset → revaluation result.

# 3. BusinessFact / EconomicOccurrence

A canonical occurrence records what the enterprise accepted as having happened.

Required properties conceptually include:

- enterprise identity;
- semantic application / transaction type;
- occurrence identity;
- effective time;
- recorded/accepted time;
- actor/provenance;
- semantic business fields;
- immutable version/identity;
- deterministic ordering identity or an input from which it is assigned.

A fact may be valid even when final monetary valuation is unresolved.

Therefore:

> Fact existence MUST NOT depend on cost already being known.

Business facts are append-only. Corrections, cancellations and reversals are new facts/instructions.

---

# 4. Measurement

Measurement is now promoted from candidate to a **supporting core primitive**.

A Measurement means:

`value + unit + semantic role + context`

Examples:

- 100 PCS of material;
- 500 KG of copper;
- USD 10,000 held/settled;
- 8 HOURS;
- 1200 CNY directly supplied business amount.

Measurement does **not** replace semantic fields such as customer, material, production date, warehouse or project.

It exists so quantity, money, foreign currency and other measurable resources do not need to be forced into one `quantity/amount/foreignAmount` schema.

A semantic role distinguishes, for example:

- resource quantity;
- direct business amount;
- foreign settlement quantity;
- valuation amount;
- reporting amount.

---

# 5. Position

A Position is derived open/current economic state.

Examples:

- unconsumed inventory quantity;
- pending production quantity;
- open receivable/payable;
- remaining foreign-currency position;
- open order quantity.

A Position is not the immutable event history.

It may be recomputed from:

`facts + allocation results + policies`.

Legacy `WaterBal / TbMatched` fields are evidence of position materialization, not canonical truth.

---

# 6. Allocation

Allocation is frozen as a generic source-consumption semantic layer.

## 6.1 AllocationInstruction / Constraint

Canonical when explicitly supplied by business/user behavior.

Examples:

- “settle this payment against invoice X”;
- “this return refers to shipment Y”;
- “consume lot L”;
- “this completion belongs to work order W”.

The instruction preserves business intent.

Minimum provenance conceptually includes:

- instruction ID;
- enterprise;
- consuming fact;
- source selector/identity;
- mode;
- actor;
- effective/recorded time;
- reason where relevant;
- policy/version context;
- correction/supersession lineage;
- idempotency identity.

## 6.2 AllocationPolicy

Versioned module/template contract defining:

- source eligibility;
- dimension scope;
- source ordering;
- selector semantics;
- partial allocation;
- residual policy;
- negative-position policy;
- precision/rounding;
- deterministic tie-breakers.

## 6.3 AllocationRelation

Generated edge:

`source position → consuming occurrence → allocated measurement(s)`.

It records lineage back to:

- facts;
- explicit instruction if present;
- policy/version;
- execution/run;
- ordering context.

Automatic allocation is rebuildable.

A manual instruction can still produce multiple derived AllocationRelations after splitting.

# 7. Cost basis and valuation

EVO freezes a distinction between **basis evidence** and **basis result**.

## 7.1 Explicit Basis Evidence

Canonical business evidence when directly supplied/accepted.

Examples:

- purchase acquisition amount;
- contracted settlement amount;
- explicitly accepted transaction-rate snapshot;
- source basis carried by an identified transfer where that linkage is business evidence.

## 7.2 CostBasisResult

Derived normalized valuation basis created from:

- explicit basis evidence;
- allocations;
- source-basis carry-over;
- manufacturing/transformational derivation;
- cost method policy.

This avoids the incorrect blanket statement “cost is never factual”.

The correct rule is:

> Cost interpretation is derived; some inputs to that interpretation are canonical business basis evidence.

---

# 8. CostMethodPolicy

One runtime substrate supports required methods.

## FIFO
- source scope = valuation pool;
- ordering = oldest eligible source first;
- allocation = layer consumption.

## LIFO
- same substrate;
- ordering = newest eligible source first.

Strict historical LIFO was not evidenced in legacy code, but the architecture supports it without a separate model.

## Moving / Weighted Average
- valuation scope = pool;
- price = pool amount / pool quantity under explicit precision/residual policy;
- per-receipt outbound matching is not required for valuation.

## Specific Identification
- explicit selector / AllocationInstruction chooses source identity;
- source basis is propagated from that identified source.

## Latest-In Price
Legacy `lastStockIn()` is explicitly classified as a distinct reference valuation method if ever retained.

It is **not LIFO**.

Cost method and negative-position policy remain orthogonal.

---

# 9. Currency and FX

Currency has two non-collapsible roles:

1. economic resource/denomination that can be held, transferred or settled;
2. unit used to express valuation/reporting.

EVO rejects one generic `exchangeRate`.

Rate roles include at least:

- transaction/recognition rate;
- settlement rate/basis;
- period-end valuation rate;
- reporting conversion rate.

Every deterministic rate use binds:

- semantic role;
- currency pair/base currency;
- effective date/time;
- provider/source;
- immutable dataset/version;
- precision/rounding;
- lineage.

## 9.1 Realized FX

`settlement occurrence + allocation closes foreign position → remaining local carrying value → realized FX result`.

## 9.2 Period-end revaluation

`open foreign position + period-end rate dataset → valuation result/delta`.

Revaluation does not rewrite foreign quantity or original business facts.

---

# 10. Projection and ledger

Posting/ledger infrastructure remains valid, with a refined role.

LedgerEntry is a deterministic **projection**, not canonical enterprise fact.

PostingRule / ProjectionDefinition decides how business/economic evidence and authorized derived inputs create:

- operational ledger effects;
- financial accounting entries;
- management/project/org projections.

Operational and financial ledgers may share infrastructure.

Ledger balance remains a rebuildable materialization:

`balance = projection over ledger entries`.

Existing `LedgerEffect(quantity, amount, unit, currency, dimensions)` remains a compatible physical/API representation, but future evolution should allow explicit typed measurement semantics without forcing all domains into only quantity/amount.

---

# 11. Valuation posting

ADR-0014 and the existing valuation-posting boundary remain valid:

- Cost/Valuation Result does not mutate LedgerBalance directly;
- valuation posting creates deterministic LedgerEntry effects;
- posting is idempotent against the reflected target value;
- valuation rule version is pinned;
- no Command or BusinessData mutation occurs during valuation posting.

Refinement:

The valuation input lineage must extend beyond `CostResult → LedgerEntry` back through:

`fact / measurement / basis / allocation / policy / valuation run`.

---

# 12. Lineage graphs

EVO freezes these graph semantics as distinct:

1. **Business Causality Graph**  
   which business occurrence caused/authorized another.

2. **Allocation Graph**  
   which open source was consumed by which occurrence.

3. **Valuation / Cost Derivation Graph**  
   which basis/pool/allocation contributed to a value.

4. **Projection Lineage Graph**  
   which fact/result/rule generated which ledger/projection.

5. **Calculation Dependency Graph**  
   which derived object must be recomputed when another changes.

They may share infrastructure but MUST NOT be collapsed into one generic parent/source relationship.

---

# 13. Replay

Full deterministic replay is the correctness oracle.

`Canonical Facts`
` + Explicit Instructions/Basis Evidence`
` + Pinned Template Definitions`
` + Pinned Rules/Policies`
` + Pinned Reference Datasets`
` + Deterministic Ordering Contract`
` → Derived State`.

Replay does not re-execute Commands.

Commands are decision-time request/authorization mechanisms. Replay consumes accepted canonical facts/evidence.

## 13.1 Full replay

Must be possible without trusting current materializations.

## 13.2 Incremental replay

Allowed as a performance optimization:

`Change`
` → ImpactRoot`
` → DependencyClosure`
` → EarliestAffectedBoundary`
` → ValidCheckpoint?`
` → DeterministicRecompute`
` → Verify`
` → Activate`.

Required invariant:

`digest(incremental result) == digest(full replay result)`

for identical pinned semantic inputs.

If safe equivalence cannot be established, fall back to full replay.

---

# 14. ReplayCheckpoint

ReplayCheckpoint is explicitly **not canonical truth**.

It is a rebuild acceleration artifact binding at least:

- enterprise/scope;
- boundary ordering identity;
- ordered input digest;
- last included fact;
- template version;
- posting/allocation/cost/valuation policy versions;
- reference dataset versions;
- runtime semantic version;
- dependency graph/version identity;
- materialization/result digest;
- validity conditions;
- provenance.

A backdated fact or retroactive semantic change may invalidate it.

---

# 15. Ordering

The architecture freezes the distinction between:

- business/effective order;
- allocation candidate order;
- calculation dependency order;
- posting/replay sequence;
- materialization execution order.

They MUST NOT be assumed identical.

A deterministic execution order must use explicit semantic keys and stable tie-breakers rather than physical DB insertion IDs.

Candidate common contract:

`effective_time + explicit semantic sequence + stable deterministic tie-breaker`.

Domain policies may define additional ordering.

---

# 16. Runtime mode / replay isolation

Initial runtime may continue using a simple pause/rebuild strategy, but architecture is frozen around an explicit replay epoch/mode boundary.

Candidate state family:

- LIVE;
- REPLAY_PREPARING;
- REPLAY;
- REPLAY_VERIFYING;
- RECOVERY.

During replay:
- authoritative writes to affected derived/materialized scopes are paused or isolated;
- a fact input boundary is pinned;
- candidate state is rebuilt;
- invariants/digest are verified;
- activation is atomic at the logical dataset/epoch boundary;
- later facts continue after that boundary.

This supersedes queue-clearing as an architectural abstraction while allowing a simple implementation initially.

---

# 17. Materialization

Materialization is first-class and intentional.

Allowed examples:

- ledger balances;
- open positions;
- moving-average pools;
- cost snapshots;
- work queues;
- reporting aggregates;
- search/read models;
- replay checkpoints.

Every materialization should declare, where applicable:

- canonical/derived sources;
- derivation version;
- purpose;
- refresh/consistency model;
- rebuildability;
- lineage/run identity.

Frozen principle:

> **Semantic Normalization, Physical Denormalization.**

---

# 18. Template versus runtime

The Economic Runtime is generic.

Industry/application meaning lives in versioned Enterprise Template definitions such as:

- TransactionType / Application;
- semantic fields;
- PositionDefinition;
- LedgerDefinition;
- PostingRule / ProjectionDefinition;
- AllocationPolicy;
- CostMethodPolicy;
- ValuationPolicy;
- Dimension definitions;
- Rate/Reference policy;
- process/work definitions.

The core runtime executes these definitions deterministically.

It does not hard-code manufacturing, sales, APM or any single industry as the canonical core.

# 20. Rejected mappings / anti-patterns

The following are now explicitly rejected:

- `foreignAmount` as a universal canonical core primitive;
- one generic `exchangeRate`;
- mutable WaterBal/TbMatched as source truth;
- mutable balance as source truth;
- a monolithic legacy `Component` as one EVO core object;
- `c_match_rel` as a one-to-one canonical Allocation object;
- a single overloaded `source_id` / `parent_id` for all lineage;
- latest-in price treated as LIFO;
- DB insertion ID as semantic replay order;
- implicit “latest rule/rate/policy” during deterministic replay;
- replay by re-executing Commands;
- incremental recalculation as a correctness source;
- hard-coded account/ledger IDs as generic recalculation scope;
- destructive edits to historical facts for correction/revaluation;
- letting materialization implementation define semantic truth.

# 21. Frozen invariants

1. Accepted business/economic history is append-only.
2. A fact may exist before final valuation is resolved.
3. Measurements carry explicit units and semantic roles.
4. Business semantic fields remain first-class.
5. Explicit allocation intent is preserved; algorithmic allocation is rebuildable.
6. Positions are derived open/current state.
7. Basis evidence and derived valuation basis are distinct.
8. Cost methods are policies over a shared Allocation + Valuation substrate.
9. FX settlement and period-end revaluation are distinct derivations.
10. Rate roles and datasets are explicit/versioned.
11. Derived projections never silently rewrite facts.
12. Balances/materializations are rebuildable.
13. Lineage graph semantics remain distinguishable.
14. Full replay is the correctness oracle.
15. Incremental replay must prove equivalence or fall back to full replay.
16. Replay uses pinned versions/datasets and deterministic ordering.
17. Replay checkpoints are optimization artifacts with validity conditions.
18. No LLM participates in authoritative deterministic runtime execution.
19. Template definitions are versioned and explicit.
20. Physical optimization may denormalize; semantic truth remains normalized and traceable.

# 22. Implementation sequence after freeze

Architecture implementation proceeds additively:

1. freeze/public interfaces;
2. invariants and tests;
3. schema/migrations;
4. Allocation contracts/runtime;
5. Measurement/basis/rate contracts;
6. cost/valuation compatibility adaptation;
7. dependency graph + replay checkpoint contracts;
8. incremental replay implementation only after full-replay equivalence tests;
9. observability and lineage queries;
10. Enterprise Template normalization/mapping;
11. reference scenarios and certification.

No broad database rewrite should precede the contract/invariant layer.

# 25. Freeze result

The Economic Runtime semantic architecture is now frozen at v0.1.

This does **not** mean implementation is complete.

It means future implementation changes must converge toward these boundaries and cannot silently redefine:

- what is canonical;
- what is derived;
- what is materialized;
- what is a versioned policy;
- what replay means;
- what lineage must preserve.

Next work phase:

`Economic Runtime Contract Convergence & Implementation`

followed by continued complete Enterprise Template archaeology/certification.
